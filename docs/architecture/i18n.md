# Internationalization (i18n)

The app ships English only but is built to add locales without touching feature
code. Localization uses **LinguiJS** (compile-time macros, compiled catalogs - no
runtime ICU parser) with the native **`Intl`** API for number/unit formatting.

## Where things live

- `src/shared/i18n/` - the runtime (a leaf layer; imports nothing internal):
  - `i18n.ts` - the global `@lingui/core` `i18n` instance.
  - `setup.ts` - locale resolution, activation, lazy catalog loading, and
    `<html lang/dir>` sync. `initI18n()` runs once in `main.tsx` before render.
  - `formatters.ts` - memoized `Intl.NumberFormat` helpers (distance, percent,
    plain decimal). Numbers/units are formatted here, with one documented
    exception (editable fields, below).
  - `locales.ts` - the supported-locale list and per-locale text direction.
  - `locales/<locale>.po` - the committed message catalogs (source of truth).
- Provider: `main.tsx` wraps the app in `<I18nProvider>`.

## Authoring strings

- **Visible JSX text** -> `<Trans>` from `@lingui/react/macro`.
- **String attributes** (aria-label, title, placeholder) -> `t` from the
  `useLingui()` macro hook: ``aria-label={t`Close`}``.
- **Copy tables consumed by a component** (error copy keyed by kind, fallback
  branches) -> a module-level map of `msg` descriptors, resolved in render with
  `i18n` from `useLingui()`. Do not import the global `i18n` instance in
  component code.
- **Non-React code** (Zustand action files building announcements/toasts) -> the
  `msg` macro from `@lingui/core/macro`, resolved at fire-time with
  `i18n._(descriptor)` on the global instance.
- **Counts** -> the `<Plural>` / `plural` macro.
- **Numbers/units** -> the `formatters.ts` helpers, never inline `.toFixed()`.

`eslint-plugin-i18next`'s `no-literal-string` fails the build on new hardcoded
JSX text and on literal `aria-label`/`title`/`placeholder`/`alt` attributes (the
strings no visual review catches). Genuinely non-translatable text (proper
names, URLs) is held in a named constant and rendered as `{expression}`. Strings
built in non-React `.ts` files are not lint-covered; the pseudo-locale e2e spec
is the net for those.

## Loading & performance

English is imported statically and activated synchronously at startup, so the
default path has **no async gate and no first-paint flash**. Every other locale is
a lazily `import()`-ed chunk (named `locale-*` for the bundle-budget gate) fetched
only when activated, so the shell never carries an inactive locale. The compiled
English catalog adds a few KB to the shell.

## Locale selection

`initI18n()` resolves `?lang=<locale>` (a QA/E2E override and future embed hook,
never a canonical signal) -> `localStorage` -> `navigator.language` -> `en`, then
reflects `lang`/`dir` on `<html>`. There is no path indicator because as an app
there are no direct SEO needs nor other reasons to manage routes. Nothing writes
the `localStorage` key yet; reading it is the forward contract for an in-app
locale switcher.

Today the locale is resolved once, before first render, and does not change for
the life of the page. The system does **not** depend on that: `<Trans>`/`t`
re-render through `I18nProvider` on `i18n.activate()`, non-React strings resolve
at fire-time, and formatters key off the active locale per call - so a live
switch would render correctly almost everywhere. The exception is the few places
that _store_ an already-resolved string: field-error strings held in component
state, and toasts already on screen. An
in-app switcher can therefore either (a) write the storage key and reload -
simplest, and cheap since drafts persist continuously - or (b) call a live
switch and clear/flush those stored-string surfaces. Audit that list before
building one.

## Not localized

- **Manifest-provided labels** - furniture names and the environment finish
  labels (wall/floor/lighting) come from `public/catalog-manifest.json`, not
  the Lingui catalogs, so they render and announce in their manifest language
  under every locale (including `en-XA`). Localizing them needs the manifest
  schema to carry per-locale text, which is outside this system's boundary.
  The pseudo-locale e2e spec exempts them by reading the manifest.
- **Brand and proper names** ("Room Layout", author, repository) are held in
  named constants (`APP_NAME` in `src/shared/messages/app-identity.ts`, local
  constants in project info) and render verbatim under every locale.
- **Editable numeric fields** (`selected-details-view.tsx`) deliberately format
  with a fixed `.` decimal separator because the commit path parses drafts with
  `Number()`, which only accepts `.`. Shipping a locale whose keyboards produce
  `,` decimals needs locale-aware input parsing first; until then this is a
  documented exception to the formatters rule.

## Testing

- Component/unit tests render through `src/test/render.tsx` (wraps
  `<I18nProvider>`); English is activated in `vitest.setup.ts`, so Lingui renders
  source English and existing text assertions keep working.
- `e2e/i18n-pseudolocale.spec.ts` loads `?lang=en-XA` and asserts, via DOM
  measurement (not screenshots), that the split catalog activates, no source
  string leaks untranslated, every `aria-label` is localized (manifest furniture
  names exempt), layout survives the length expansion, and full axe conformance
  holds - on the editor surface and inside the catalog drawer and project info
  dialog. It resolves expected accessible names from the committed `en-XA.po`,
  so it needs no hardcoded pseudo text. This catches gross layout breakage
  (horizontal overflow); add targeted per-element assertions (in-viewport, not
  clipped) when you find a specific control that mishandles long text. When you
  add a user-facing surface, open it in this spec.

## Adding a locale

1. Add the code to `SUPPORTED_LOCALES` + `LOCALE_DIRECTION` in `locales.ts` and a
   loader in `CATALOG_LOADERS` in `setup.ts`.
2. Add it to `locales` in `lingui.config.ts`, run `pnpm i18n:extract`, translate
   `locales/<locale>.po`.
3. The bundle-budget gate will flag the new `locale-*` chunk until you confirm a
   budget for it.

For an RTL locale, set its direction in `LOCALE_DIRECTION` and review the
deliberate physical-CSS cases in
[UI Components Policy](ui-components.md#logical-css-properties): those are the
spots that do not follow `dir` and may need `:dir()` handling.

## Tooling

- `pnpm i18n:extract` - scan source, update the `en` catalog, and regenerate the
  `pseudo` catalog.
- `pnpm i18n:check` - the same, then fails on any modified or newly created
  catalog file (CI drift gate).
- The `en-XA` pseudo-locale catalog is generated from `en` by
  `scripts/generate-pseudo-catalog.mjs`: accent each letter, expand length (short
  labels most), and bracket each string. ICU plural/select messages are bracketed
  but left un-accented so their structure is not corrupted. Never hand-edit
  `en-XA.po`.
